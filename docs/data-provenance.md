# 数据来源与期望值方法

历史工作簿同时包含他人整理的标签和作者手工记录的经营数据。公开包提供从该工作簿提取的游戏数据快照，网页默认使用真实角色；合成数据作为独立的规则验证输入保留。合成数据中的人物、配方、价格和数量均为虚构，不用于证明真实游戏收益。

## 字段来自哪里

| 字段或内容 | 历史数据来源 | 已知范围与限制 |
| --- | --- | --- |
| 标签，包括料理、食材及顾客偏好相关标签 | 作者确认从 [AnYiEE 的东方夜雀食堂小助手](https://github.com/AnYiEE/touhou-mystia-izakaya-assistant) 下载标签数据 | 尚未逐字段核对具体上游版本；不据此推定全部配方同源 |

| `Sell Price`、`Buy Price` | 作者将这些字段列入手工记录及期望计算的说明 | 不假定所有行采用同一估计方式；也不假定每个对象的售价都随机波动 |
| `Average Buy Price` 等派生价格 | 根据来源渠道的价格和数量进行数量加权 | 需要检查分母范围、委托处理和名称关联，不能只信旧公式缓存 |
| 配方、基础食材清单及其他未明确提及的字段 | 尚未完整确认 | 不统一声明来自上游，也不默认全部原创 |
| 公开包的合成演示数据 | 本次整理时人工编写并由 AI 辅助制作 | 与历史实测值分开，不表示真实游戏分布 |

库与素材的许可范围见[第三方组件与来源说明](../THIRD_PARTY_NOTICES.md)。这里记录字段来源与计算含义，不代替许可声明。

## 数量加权的采购期望

假设一种食材可从多个渠道获得。对渠道 `i`，`p_i` 是用于计算的单位采购价，`q_i` 是对应数量。在价格和数量记录口径一致、总供给大于零时，采用：

```text
数量加权单位采购期望 = Σ(p_i × q_i) / 总供给
```

总供给必须包含分子所对应的全部来源。只有两个普通采购渠道时，若渠道 A 以 4 元提供 5 份，渠道 B 以 6 元提供 15 份，则结果为 `(4×5 + 6×15) / 20 = 5.5` 元每份。这是解释公式的虚构例子；不能直接取两个价格的简单平均 5 元，因为数量权重不同。

旧表的部分计算把委托供给计入总供给，却没有为其计入采购支出。这等价于在该表口径下把委托份额按零采购现金支出处理。它只是旧表假设，不代表委托真正没有成本：时间、机会成本、委托的其他代价均未在这个价格中计入。若这些成本影响决策，应加入相应渠道成本后重新计算，不能把该结果直接称为完整经济成本。

当 `p_i`、`q_i` 本身来自对波动的估计时，这个结果更准确地说是基于记录的数量加权经验估计。不同观测日期如何汇总、价格与数量是否相关、渠道是否稳定可得，都会影响结果。当前没有足够原始记录来恢复完整采样分布，所以不报告样本量、置信区间或统计验证结论。总供给为零时应标为不可计算，不能将除零结果填成零成本。

## 旧价格引用错位如何处理

审计发现，旧工作簿 `食材` 表的采购价按行号直接引用 `食材merchant_data` 的平均价格。例如 `食材!F2` 对应八目鳗，而引用的 `食材merchant_data!P2` 对应蜂蜜。两个表排序不同，行号相同不代表同一食材，因此历史利润排名不能直接沿用。

本次整理通过 [`tools/prepare_data.py`](../tools/prepare_data.py) 按食材名称建立关联：读取 XLSX 中已有的缓存值，从商贩表按 `Name` 匹配 `Average Buy Price`，修正导出 JSON 中食材的 `Buy Price`，并生成逐条导入报告。它保留作者在商贩表中已有的期望计算，不重新计算商贩公式。缺少公式缓存或出现 `#DIV/0!` 等不可用值时保留为 `null`，不当作零价格，也不用另一行的价格兜底。修正发生在导出 JSON 中，原始工作簿保留作证据，不覆盖历史记录。

该修复需要与供给排序区分。当前批量规划的主要目标是喜好覆盖、食材件数和日供给余量，不使用单位采购价计算利润；把价格关联修正不等于新增了利润最优化功能。

## 日供给与采购价是两个指标

`Total Daily Quantity` 表示模型输入的日供给估计。它不等于玩家当前库存，不是保证每天都能取得的最低数量，也没有包含对所有顾客的联合消耗分配。

单客方案比较使用 `min(q_i - K × c_i)`：对该方案所用食材，分别用日供给减去假设订单数乘每份用量，再取最小值。这个 `supply_margin` 是在输入假设下的比较指标，可以为负；不同顾客共享同一种食材时，不能把各自结果看成同时成立的库存承诺。数量加权采购价估计的是金额口径，供给余量衡量的是数量压力，两者不能互换。

### 工作簿结构

工作簿包含以下四张表，首行为英文表头。每条命名数据行映射为 [demo.json](../data/demo.json) 中 `sheets` 对应表的一个对象。`Name` 在各表内唯一，跨表关联和配方引用须保持名称一致。

| 表名 | 规划核心字段 | 可选字段示例 |
| --- | --- | --- |
| `食材` | `Name`、`Tags`（可空） | `Level` |
| `料理` | `Name`、`Cookware`、`Sell Price`、`Required Ingredients` | `Tags`、`Forbidden Ingredients`、`Owned`（建议显式填 0／1） |
| `稀客` | `Name`、`Preferred Tags`（可空，无喜好时无方案）；网页另需 `Type=rare` 或 `稀客` | `Disliked Tags`、`Budget` |
| `食材merchant_data` | `Name`、`Total Daily Quantity` | `Average Buy Price`（可空） |

“核心”说明字段用途，不表示所有字段均不可空；其余可保留字段见导入器的 [`FIELDS`](../tools/prepare_data.py#L15)。每种食材须有同名商贩行，日供给为有限非负数。

标签与配方可用顿号、中英文逗号或分号、斜线、竖线、换行或制表符分隔，普通空格不分隔。两份同种食材写作 `豆腐、豆腐`，重复项保留为用量。

公式须先在电子表格软件中重算并保存缓存；导入器只读缓存、不计算公式。缺失供给缓存会阻止导入，未知均价保留 `null`。

浏览器可用 SheetJS 在本地读取真实游戏工作簿。若要为 Python 规划器准备 JSON，同时修正上述价格关联并查看导入记录，可运行：

```bash
python tools/prepare_data.py my.xlsx --output local-data/game-data.json --report local-data/import-report.json
```

`my.xlsx` 由使用者提供。新导入的数据和报告默认写入被 Git 忽略的 `local-data/`；它们不会自动替换随仓库提供的 `data/game.json`。公开包不附带整本工作簿或第三方攻略。输入文件、分析报表与规划结果的区别见[输入输出说明](input-output.md)。

继续采样时，建议记录观测日期、游戏版本、渠道、单位价、数量、委托数量与成本口径；将原始观测和聚合结果分开保存。这样后续可以复算数量加权值，比较版本变化，并检验当前供给假设是否适合自己的游玩方式。现有数据缺少的记录保持为未知，不通过估计补写成历史事实。
