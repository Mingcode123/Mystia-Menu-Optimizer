# 从游玩问题到料理规划：我的需求演进复盘

这篇复盘沿着实际备菜问题，整理我在历史 prompt 中逐步明确的规则、目标与取舍。文中的 prompt 要点是对需求的转述，不是逐字引用；章节按问题演进组织，不代表分支对话的精确时间顺序。

我最初希望得到一个能帮助自己求最优解的程序。项目的主线是：**把《东方夜雀食堂》中“给不同顾客准备什么料理”变成优化问题，再随着实际需求明确，逐步调整“最优”的定义。**

这里有两条不同的迭代线：一条改变优化问题本身，例如从每标签多方案改成每客单方案，将喜好覆盖收益封顶，再加入厨具限制；另一条在问题不变时改进求解方法，要求加速仍保持目标和结果一致。历史 prompt 中既有明确的需求变更，也有对错误实现和结果变化的追查，不能把它们全部归为功能增加。

我负责提出游玩需求、澄清机制、调整指标和约束，并用具体角色检查输出。大量代码实现与部分调试由 AI 辅助完成。下面关注的是这些 prompt 如何形成设计，而不是罗列使用过多少次 AI。

## 起点：为具体顾客找到满足要求的料理

最初的需求围绕具体的料理选择：给定稀客、喜好和希望满足的标签，找出达到分数门槛的基础料理与加料方案。要让程序回答这个问题，先得把游玩时能凭经验理解的机制说清楚。

**当时 prompt 的核心要求：**枚举能达到三分的料理与加料组合，计入喜好和厌恶，遵守五格限制、禁忌与标签覆盖关系。

最早的请求还包含“按照实际利润排列”。因此，收益比较确实属于起点，不能从复盘里抹去；但后来的求解主线转向食材件数和供给余量。售价、利润和食材件数不是同一个目标，当前程序也没有实现完整现金利润最优化。

进一步的澄清落在几个容易误解的细节上：基础配方会消耗食材，但不能把基础食材标签再次加到料理上；允许重复加入同一种食材，重复份数占格，标签却只计一次；“小巧”来自料理自身，不能把一份食材自动等同于小巧；“肉”“重油”等标签会覆盖其他标签。

这些要求决定了程序在计算什么。如果基础标签或覆盖顺序错了，即使输出了很长的结果表，也不能拿来辅助备菜。这个阶段，我的 prompt 主要承担规则说明和边界澄清的作用。

## 数据准备：把标签资料与经营观察分开

标签资料来自 AnYiEE 的项目。价格、每日供给、委托数量等经营相关字段，则包含我在游戏中手动记录并计算期望的工作。两类资料为不同问题服务：标签决定料理能否满足偏好，数量与价格帮助描述获取食材的条件。

对话中还讨论过表头和变量名称，例如使用 `Preferred Tags`、`Required Ingredients`，以及区分配方禁忌 `Forbidden` 和使用者主动设置的排除条件 `Excluded`。

**当时 prompt 的核心要求：**让字段名称与代码含义对应，区分游戏制作规则、玩家筛选条件和仅供参考的信息。顾客 `Budget` 明确只展示，不参与当前计算。

我要求表头与代码中的变量名称一起对应，而不是只显示一个新名字、内部继续使用含义不清的旧词。配方禁忌、玩家排除、基础耗用、追加标签和展示预算分别承担什么作用，也需要讲清楚。这些决定了哪些字段会进入可行性判断、目标函数或输出表。

这一步让数据表不只是材料列表，也逐渐成为模型的输入约定。手工记录的期望值仍有边界：当前留存材料不能恢复完整采样次数与分布，不能把估计值当作确定常数。具体来源和估计口径见[数据说明](data-provenance.md)。

## 候选变多后：定义什么方案值得留下

能枚举可行组合之后，下一步是筛选。我的要求逐渐细化为加料子集过滤、高级食材替代、等价食材去重，以及是否把得分纳入过滤条件。

**当时 prompt 的核心要求：**等价关系只作用于额外加料，不能替换基础配方；“高级”按食材标签的真子集关系判断，不能直接用 `Level`；移除某个高级方案之前，必须存在合法的低级替代方案。

这里的关键是给“优化”设定条件。仅仅看到某种食材标签更多，不能直接决定它更好；仅仅能找到标签更少的替代食材，也不能推断替代后的整份料理仍然达标。因此，过滤应检查方案是否成立，以及分数是否符合所选策略。

是否“考虑得分”也被做成可选条件：有时关注的是达到门槛后减少冗余，有时需要保留得分更高的组合。prompt 开始表达筛选策略，而不只是要求结果越少越好。

过滤的位置同样重要。我曾明确纠正：高级食材过滤删的是完整方案，必须等合法低级替代方案存在后再判断，不能在生成候选之前凭食材名称或 Level 删除。后来用露米娅、流行喜爱“和风”和饭团等具体结果检查这些选项是否真的按定义工作。

从现在的模型角度看，需要区分三件事：用户选择的候选保留策略、仅压缩表示的等价处理，以及为加速而跳过搜索分支的剪枝。尤其加入供给指标后，标签相同并不代表所有目标都相同。历史上要求“结果不变”是验收标准；旧代码是否在每个边界都保留了最优解，仍要依据实现核对。

## 加入供给：让推荐考虑食材取得条件

不同食材的每日取得数量不同。标签相同或得分相同的方案，可能给采购带来不同压力。因此，我开始把每日供给和假设订单量纳入方案比较。复盘时需要说明，这里的食材件数与采购金额是不同指标。

历史上，我先讨论枚举不同的标签覆盖组合及其订单责任分配，比较总食材数期望；期望相同，再找最低供给余量更大的安排。随后讨论按每个喜好标签分别准备方案的模型，把第一目标拆成每标签最少食材，再通过 λ 可行性判定搜索第二目标。这里的要求是用等价改写减少计算，同时保持原来要找的最优结果。

这里的“责任”指一份料理承担哪些标签对应的订单份额。一份料理可以覆盖多个标签，但标签命中本身还没有确定各食材的预期消耗，因此覆盖关系与订单分配需要一起考虑。

**当时 prompt 的核心要求：**把优先最少食材、随后比较供给余量的顺序写清楚，并说明订单量怎样进入计算。

将这条要求与旧代码对照，可以看出两阶段的理由：先为每个标签保留全部并列最少食材方案，再在它们之间挑选供给更宽裕的组合。若日订单量为 $`K`$、参与规划的标签数为 $`m`$，食材 $`i`$ 在这些方案中的累计用量为 $`u_i`$，旧模型按 $`(K/m)u_i`$ 估计日消耗。这依赖订单均分假设，不是我实测出的标签订单概率；旧代码的 $`m`$ 实际只计有可行候选的标签。

λ 讨论则把“最大化最低余量”改成逐次提问：“能否选出一组方案，让每种实际使用食材至少剩下 $`\lambda`$？”门槛越高，要求越严格；较高门槛可行，较低门槛也可行。这一单调关系是当时讨论二分与可行性搜索的依据。二分没有消除内部组合判定的成本，不能据此把整个求解过程称为对数复杂度。完整公式与旧实现的边界见[数学建模说明](design.md#数学建模从历史多方案到当前单方案)。

这一阶段的设计问题是：好方案除了满足顾客，还应怎样对待资源？“最少食材件数”“最低采购金额”“最高售价”“供给更宽裕”是不同目标，不能用一个模糊的“成本最低”将它们混在一起。

历史求解讨论属于迭代过程，不表示这些算法全部成为当前默认实现，也不能仅凭当时 AI 的解释认定正确性或最优性。

## 改变决策单位：从每标签一套，转为每顾客一套

随后，我明确要求从每个喜好标签一套方案，改成每位稀客一套方案。这改变了工具要交付的答案：从针对不同标签分别准备，转向为一位顾客选择覆盖多个喜好的料理。

**当时 prompt 的核心要求：**每位稀客输出一套方案，先比较喜好覆盖，再比较总食材件数，最后比较供给余量。

这个变化同时改变了最优对象和目标顺序：原来比较多套方案的组合，先最少预期件数，再改善供给；现在比较一份料理，先尽量覆盖更多喜好，再考虑件数与供给。两个版本解的是不同问题，输出不必相同。

同一套游戏资料，由于决策单位改变，会形成不同的优化问题。这个阶段体现的取舍，是明确工具究竟要回答“每类要求怎么满足”，还是“面对这位顾客准备什么”。

## 调整边际收益：覆盖三个之后，优先少用食材

单方案模型起初按覆盖更多喜好优先。后来我明确提出：喜好覆盖达到三个即可，之后先最少总食材，再最大化补给余量。

**当时 prompt 的核心要求：**将覆盖收益封顶为三个，按照“覆盖收益 → 总食材件数 → 最低供给余量”的先后顺序比较方案。

这一变化比简单调整一个权重更明确。例如两个方案都达到三项喜好，其中一个继续追加食材命中第四项；在新的目标下，第四项不再带来覆盖收益，增加食材需要让位于少用食材的目标。

用收益函数表示就是 $`U(h)=\min(h,3)`$，所以第四项喜好的边际收益 $`U(4)-U(3)=0`$。我改变了“达标后什么值得继续追求”的定义，并按覆盖收益、食材件数、余量逐项比较；没有把三项加成一个可以互相补偿的加权总分。

这里的“三个”是我为工具设定的目标收益边界，不意味着证明游戏只计算三个标签。当前 Python 默认最低分也是三，且排除厌恶，因此合格候选的封顶覆盖相同，后续主要比较食材件数和余量。

这成为项目最清楚的一项设计选择：满足核心要求后，停止追逐对当前使用目标帮助有限的更高指标。

## 加入厨具：把单份料理放回备菜环境

后续要求加入排除指定厨具，以及从可用厨具中选择限定数量的功能。问题随之扩展：单看每位顾客都有方案，并不代表这些方案能在同一组厨具条件下使用。

**当时 prompt 的核心要求：**支持排除烧烤架、蒸锅等厨具，比较限定厨具组合下各位顾客的方案。

在默认三分条件下，厨具组合先争取让更多顾客有合格方案，再比较食材件数和供给余量。没有合格方案的顾客也应明确显示，方便追查是规则、标签还是设备条件限制了结果。

我还用古明地恋等具体角色，对比“限定三件厨具”和“排除两件厨具”得到的结果。对相近配置提出一致性问题，是这一阶段的重要验收方式。

设备约束只统一了厨具选择，并没有把多位顾客的食材消耗共同扣减。当前工具依然不能保证整晚共享库存足够。

## 并行主线：在 CPU 上求得更快，同时保持结果

原型开发时，我的电脑没有可用的 GPU。这是我在本次复盘中补充的硬件背景；现有共享页可读取的文字中没有找到这句硬件原话，但多次保结果提速的要求有直接记录。例如：“理解一下算法，看看有没有能在不改变所有选项运算结果的情况下提高运算速度”，以及“stage2 还是太慢了，想办法提高计算速度但是不改变结果”。

我的要求也不止于缩短等待：开启过滤后卡在 0%、某个料理或角色长时间无进展、另一个实现已经能产生候选而当前版本仍卡住，都会成为进一步检查的触发点。我要求先解释逻辑，指出究竟在哪一步产生了过多组合或重复工作，再修改代码。

**当时 prompt 的核心要求：**实现可以改变，但已经确认的规则、优化目标与结果含义应保持一致。修改需求时主动说明；只提速或改排版时，不应悄悄改变模型。

对照留存代码，这条线涉及三个不同的计算规模：

| 组合增长的位置 | 原型采用的处理方式 | 需要保留的含义 |
| --- | --- | --- |
| 每道料理的重复加料组合 | 标签分组、无序多重集枚举、位集计算；部分分支以得分上界跳过不可能达标的搜索 | 重复加料合法，标签仍只计一次，不能漏掉符合规则的候选 |
| 多个标签各选一份方案 | 每道料理只生成一次候选并按标签分桶；保留并列最少件数；λ 容量判定结合 DFS 与状态缓存 | 第一目标相同的候选仍可能有不同供给表现，不能过早只留一个 |
| 共享厨具配置 | 先计算每客每厨具的最佳候选，再复用这些结果比较厨具集合 | 复用相同规则与参数下的子问题结果，不能把旧配置结果错误套入新配置 |

网页还使用后台 Worker 计算和分批回传。不同分支的优化并不完全相同：旧 perfect 分支是单 Worker 并带得分上界剪枝；根网页版按料理静态分块，最多使用 8 个 CPU Worker，但没有保留同一套得分上界。它们不是 GPU 实现，也不能把这些分支的优点合并成一项未经验证的性能成绩。

具体缓存、位集、搜索和并行代码由 AI 辅助实现。我的工作体现在提出保结果的提速要求、澄清哪些简化允许、用实例检查运行表现，并追查结果不一致。当前没有足够历史基准来复算加速倍数，外层 λ 二分也没有消除内部组合搜索的成本。

## 让长计算可观察，让参数变化可比较

流行喜爱与厌恶要分别输入，允许多字段和空输入；必含标签、分数门槛、过滤策略以及厨具条件应有明确含义。这些参数让同一个求解问题可以在不同条件下复算，而不是每次改代码中的隐含假设。

我还要求进度反馈覆盖真实完成状态：例如按十道料理更新时，总数不是十的整数倍，也必须报告最后的实际完成数，而不能停留在前一个整十数。这个例子强调的是通用规则，不能为某次的料理总数写特殊判断。

计算、界面显示和 Excel 导出也需要分清。历史上我比较过两个版本除导出外是否有算法差异，并报告某版本卡住而另一个版本没有。保留这些需求，是为了说明我关注程序能否完成一次可检查的求解；历史 AI 对具体卡顿根因的解释仍需单独验证。

## 验收：用具体结果追问规则是否真正被执行

历史 prompt 中反复出现几类要求：以指定文件为修改基准；不要误用旧底稿；只改排版时不应改变推荐结果；流行喜爱和厌恶分开输入；计算过程应有可见进度。

我曾以茨木华扇的版本结果差异追问修改是否影响算法，也用森近霖之助在特定流行厌恶条件下的无解结果检查约束。这些角色案例把“看起来不对”缩小成可讨论的输入与输出。

还有一类检查是主动给出可能的反例，例如用莉格露与具体食材组合追问覆盖关系和分数是否算错。提出反例不意味着我对每个游戏细节的初始判断都已被证明；它为核对规则提供了具体输入，也能帮助发现候选被错误删除、门槛被误用或标签处理顺序不一致。

**当时 prompt 的核心要求：**解释具体条件下为什么得到这个结果，并区分算法变化、显示变化和版本差异。

历史 AI 曾给出平局处理、缓存问题、约束冲突等解释。这些解释是排查线索，不能仅凭一段回复当成已确认的根因。现在整理作品集时，我把历史需求与本次代码验证分开记录。

## 回看：求最优解的意图与最优定义的变化

这段过程可以连成一条主线：

```text
找出满足条件的料理
  → 说清制作规则和数据含义
  → 定义候选保留与替代条件
  → 纳入日供给和目标先后顺序
  → 调整为每顾客一套方案
  → 将覆盖收益封顶为三个
  → 比较有限厨具下的备菜选择
  → 用具体角色和版本差异验收
```

我的 prompt 逐渐包含了目标、输入、硬条件、比较顺序、可选策略、输出形式和验收案例。求最优解的意图一直存在，但决策对象从多套标签方案变为单客料理，再扩展到共享厨具配置；评价标准从预期件数与供给，转为覆盖优先，再改为覆盖封顶。模型改变后，原来的最优方案不一定仍然最优。

因此，比较版本结果时应先确定目标、约束与输入是否相同。主动改变覆盖收益或厨具条件，可能合理地改变最佳方案；只修改显示或提升速度，则应保持模型含义与最优目标值。即使目标值相同，也可能存在多个并列最优方案，若还要求输出同一道菜，就需要固定平局规则。对游戏策划／数值策划而言，这段过程体现的是把游玩需求逐步明确成可求解的决策模型，并检查实现是否忠实执行这个模型。

当前成果是单客交互查询和批量规划工具。预算硬约束、酒水搭配、完整满意度、现金利润、多顾客共享库存和订单概率仍是后续可扩展的方向，不能写成已经实现的能力。
