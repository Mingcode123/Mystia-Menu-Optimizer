# 需求与设计决策演进

本章依据留存的开发对话与代码分支，梳理料理规划工具从实际游玩问题到优化模型的形成过程。历史 prompt 采用需求转述形式，章节按问题依赖组织，不对应分支对话的精确时间顺序。关于开发设备缺少可用 GPU 的背景来自作者补充回忆；保持结果一致的提速要求则有历史对话记录支持。

项目的持续目标是构建能够辅助求解备菜方案的程序。随着使用场景明确，决策对象由多个标签方案转为单客料理，再扩展到共同厨具配置；“最优”的评价标准也相应调整。与此同时，求解效率形成另一条迭代线：在既定规则和目标下减少重复计算，并通过具体角色案例核对输出。

作者承担游玩需求提出、规则澄清、数据记录、目标与约束选择及案例验收。大量代码、算法推导和部分调试使用 AI 辅助。本文重点讨论需求如何形成决策模型，实际实现与验证范围分别见[模型说明](design.md)和[验证记录](verification.md)。

## 1. 游玩问题与初始目标

初始需求是为指定稀客寻找满足得分门槛的基础料理与加料方案，并考虑喜好、厌恶、五格限制、配方禁忌与标签覆盖关系。早期需求还包括按实际利润排序，反映了经营收益比较的动机。后续 PLAN 主线逐渐采用食材件数与最低供给余量作为资源指标，完整现金利润最优化未成为该主线的实现目标。

规则澄清主要涉及以下关系：基础配方消耗食材与格数，基础食材标签不再次叠加到料理标签；同种加料允许重复，重复份数占用格数，相同标签仅计一次；“小巧”由料理属性决定，单份食材用量不自动产生该标签；“肉”“重油”等标签具有覆盖关系。

这些定义决定候选的合法性与得分。开发对话在此阶段主要用于将经验性的游戏理解转化为明确的输入条件和计算顺序。

## 2. 数据语义与输入约定

标签资料来自 AnYiEE 的项目。价格、日供给与委托相关字段包含作者在游戏中的手工记录及经验计算。标签描述偏好匹配，数量与价格描述食材取得条件，两类数据承担不同的模型职责。

字段命名逐步与计算含义对齐，包括 `Preferred Tags`、`Required Ingredients`，以及配方禁忌 `Forbidden` 与主动排除条件 `Excluded` 的区分。顾客 `Budget` 被明确设定为展示信息。字段名称与代码变量的对应要求同时涉及输入、内部处理和输出。

由此形成了数据在模型中的分工：制作规则参与可行性判断，偏好与用量参与方案评价，筛选条件表达使用策略，预算等字段提供参考信息。经验期望的采样次数与分布未完整留存，其统计适用范围见[数据来源](data-provenance.md)。

## 3. 候选保留与替代策略

候选枚举完成后，需求扩展到加料子集过滤、食材高级过滤、等价食材去重，以及是否将得分纳入过滤条件。相关要求将等价处理限制在追加食材，保留基础配方；“高级”依据标签真子集关系判断，未直接采用 `Level` 字段。

高级食材过滤以完整方案为判断对象。删除一个方案的前提是存在合法的低级替代方案，并满足所选得分策略。该条件决定过滤应在替代方案可行性得到确认后执行。对于达到门槛后减少冗余与保留更高得分两类需求，“考虑得分”被设为可选条件。

历史验收采用露米娅、流行喜爱“和风”和饭团等具体输入检查过滤效果。这些案例使筛选定义能够与实际候选对应。候选保留策略、等价表示压缩和搜索剪枝具有不同作用；引入供给指标后，标签相同的食材仍可能在资源目标上不同，策略正确性需要结合完整比较目标判断。

## 4. 资源目标与多方案配置

食材日供给的差异使相同得分或相同标签的料理具有不同采购压力。相关需求因此引入假设订单量、预期食材件数与最低供给余量，并明确采用先最少件数、后最大最低供给余量的目标顺序。

历史讨论先考虑标签覆盖组合及订单份额分配，随后形成每个喜好标签分别配置方案的模型。订单责任描述一份料理承担哪些标签对应的订单份额；料理能够覆盖多个标签时，覆盖关系与订单分配共同影响预期用量。

若每日订单量为 $`K`$、参与规划的标签数为 $`m`$，食材 $`i`$ 在所选方案中的累计用量为 $`u_i`$，旧模型按 $`(K/m)u_i`$ 估计日消耗。此处采用订单均分假设，$`m`$ 在实现中仅统计具有可行候选的标签。

相应的两阶段求解首先为各标签保留全部并列最少食材件数的方案，再比较候选组合的最低供给余量。保留并列候选具有必要性：相同件数的方案可能消耗不同食材，并产生不同的供给压力。

第二阶段将最低供给余量最大化改写为阈值 $`\lambda`$ 的可行性判定。较高阈值可行意味着较低阈值也可行，由此采用外层二分与内层组合搜索。二分减少阈值搜索次数，单次判定仍涉及候选组合。完整目标、假设与实现范围见[数学模型](design.md#数学建模从历史多方案到当前单方案)。

该阶段确立了资源指标的独立含义：食材件数、采购金额、售价和最低供给余量分别衡量不同结果，目标顺序需按备菜需求明确指定。

## 5. 决策单位调整与覆盖收益封顶

多标签模型为不同喜好分别安排方案；后续需求明确改为每位稀客输出一套料理方案，不再针对各标签分别配置。目标顺序随之调整为先最大化喜好覆盖，再最小化食材件数，最后最大化最低供给余量。

这一变化同时调整了决策单位与评价顺序。旧模型比较多套方案的组合，优先控制预期用量；单客模型比较一份料理，优先覆盖该顾客的多个喜好。两类模型对应不同的备菜决策。

后续覆盖封顶需求进一步明确了达标后的边际收益：喜好覆盖达到 3 项后，优先减少食材件数，再比较最低供给余量。覆盖收益定义为 $`U(h)=\min(h,3)`$，因此第 4 项喜好的目标边际收益 $`U(4)-U(3)=0`$。

例如，方案 A 命中 3 项喜好并使用 2 份食材，方案 B 命中 4 项喜好并使用 3 份食材。采用覆盖封顶后，两者覆盖收益相同，A 在食材件数上优先。词典序比较保留该优先级，指标之间没有加权补偿。

覆盖上限是工具的效用设计，未用于推断游戏完整评分规则。`singlePLAN_cover3_mixIng_nCookware.py` 默认最低分同样为 3，且排除厌恶命中；其合格候选覆盖收益相同，后续主要比较食材件数与最低供给余量。未封顶的 `singlePLAN.py` 保留覆盖优先的另一种评价方式。

## 6. 共同厨具约束

设备条件将问题从单份料理选择扩展到共同备菜配置。需求先涉及排除烧烤架、蒸锅等指定厨具，随后涉及从可用厨具中选择限定数量。对应实现分别采用排除列表分支与 `nCookware` 数量选择分支。

在默认最低分为 3 的条件下，厨具集合的覆盖收益比较优先增加有合格方案的顾客数，再比较食材件数与逐客最低供给余量。无解顾客保留在输出中，以支持对规则、标签与设备约束的检查。

历史验收曾以古明地恋等角色比较限定 3 件厨具与排除 2 件厨具的结果，检查相近配置的选择是否一致。共同厨具约束统一设备集合，各顾客的食材用量仍独立核算，未形成整晚共享库存的联合配置模型。

## 7. CPU 求解效率与结果一致性

计算效率问题主要表现为组合枚举耗时、过滤后进度长期停留、特定料理或角色处理缓慢，以及版本间响应差异。开发要求包含分析组合增长位置、减少重复工作，并在规则与目标不变的前提下保持结果含义。作者补充的无可用 GPU 背景，与留存代码采用 CPU 搜索和浏览器 Worker 的执行方式一致。

| 计算规模来源 | 历史原型采用的方法 | 一致性要求 |
| --- | --- | --- |
| 单料理的重复加料组合 | 标签分组、无序多重集枚举、位集计算；部分分支采用得分上界剪枝 | 保留重复加料规则、标签去重计分及符合条件的候选 |
| 多个标签各选一套方案 | 每道料理生成一次候选并按标签分桶；保留并列最少件数；采用 λ 容量判定、DFS 与状态缓存 | 保留第一目标并列而供给效果不同的候选 |
| 共同厨具集合 | 预计算每客每厨具的最佳候选，复用子问题结果 | 子问题采用相同规则与参数，缓存对应正确配置 |

网页采用 Worker 计算与分批回传。历史 `perfect` 原型（未随本仓库分发）使用单 Worker 并带得分上界剪枝；根目录网页版按料理静态分块，最多使用 8 个 CPU Worker，未采用同一套得分上界。各分支的方法与实现条件应分别解释。

具体缓存、位集、搜索与并行代码使用 AI 辅助实现，作者承担结果一致性要求、允许简化条件与案例验收的定义。历史材料未保留足够的统一性能基准，因此仅报告采用的方法，不报告加速倍数。

## 8. 参数表达、进度反馈与案例验收

参数需求包括分别输入流行喜爱与厌恶、允许多字段和空输入，以及明确必含标签、得分门槛、过滤策略和厨具条件。参数化使同一模型能够在不同条件下复算，并为版本比较提供明确输入。

进度反馈要求覆盖实际完成数量。例如，以每 10 道料理为间隔更新时，总数非 10 的整数倍也应报告最终完成数。该要求将进度显示定义为通用完成状态，而非针对某次数据规模的特殊处理。

结果验收同时区分计算、显示与导出。指定修改基准、避免误用旧版本、排版调整保持推荐结果，是历史对话中反复出现的要求。典型案例包括：

| 案例 | 检查目的 |
| --- | --- |
| 茨木华扇的版本结果差异 | 核对修改是否改变算法或平局选择 |
| 森近霖之助在特定流行厌恶条件下无解 | 检查约束与标签处理 |
| 莉格露与指定食材组合 | 以反例核对覆盖关系、得分和候选删除 |
| 古明地恋在相近厨具配置下的结果 | 检查设备约束与配置一致性 |

上述案例将检查范围限定到具体角色、参数与候选，为规则核对提供输入条件和待检验假设。历史 AI 对平局、缓存或约束冲突的解释保留为排查线索，具体结论以代码和运行证据为准。

## 9. 设计演进的综合分析

需求演进体现为决策对象、评价指标与约束的逐步明确：

双语[模型演进总览图](../README.md#zh-model)以决策对象和目标函数展示这条主线：达标候选查询 → 每标签多方案 → 每客单方案 → 覆盖收益封顶 → 共同厨具配置。HTML 与 Python 为独立入口，共享输入工作簿；这些箭头表示问题定义之间的关系，不表示程序调用关系。

`mixedingredients` 统一基础食材与加料的五格输出，属于表达调整。CPU 搜索和缓存优化属于求解方法调整。普客、酒水与利润分析属于独立支线。这些变化应与决策变量、目标函数及厨具约束的变化分别解释。

求最优解的意图贯穿各阶段，但最优方案始终依赖所定义的模型。主动调整覆盖收益或厨具条件可能改变最佳方案；仅调整显示或提升求解速度，则要求保持模型语义和目标值。存在并列最优候选时，具体料理是否一致还取决于平局规则。

最终形成的设计描述涵盖目标、输入、硬约束、比较顺序、可选策略、输出形式与验收条件。PLAN 系列的范围集中在喜好覆盖、食材件数、最低供给余量与厨具配置；预算硬约束、酒水搭配、完整满意度、现金利润、多顾客共享库存和订单概率尚未纳入联合模型。
