# 网页查询与导出指南

网页用于查询单个稀客的料理与追加食材组合，支持标签条件、候选过滤、结果排序和表格导出。数据来自 XLSX 工作簿，角色与料理图像由名称映射匹配独立资源文件。

本指南对应仓库根目录的当前网页。优化前网页及其数据、资源可从 [v1.0.0 Release](https://github.com/Mingcode123/Mystia-Menu-Optimizer/releases/tag/v1.0.0) 下载，解压后按相同方式启动本地服务；其计算与界面行为以该版本的文档为准。

## 启动与操作

可直接打开 [GitHub Pages 在线页面](https://mingcode123.github.io/Mystia-Menu-Optimizer/)。在线页面与本地版本均在浏览器中计算，手动选择的工作簿不上传至计算服务。

本地运行时，保留完整仓库目录，在根目录执行：

```sh
python -m http.server 8000 --bind 127.0.0.1
```

本地访问 <http://127.0.0.1:8000>。两种入口均按以下流程操作：

1. 页面自动读取同目录的 `东方夜雀食堂.xlsx`，也可通过文件选择器指定 XLSX。
2. 选择稀客，设置得分阈值、必含标签、排除标签及流行触发标签（例如“和风”，表示该标签触发相应的流行喜爱或厌恶）。
3. 选择候选过滤选项，点击“开始计算”。
4. 在结果区查看料理、厨具、食材、得分和最终标签，按需要搜索、筛选与排序。
5. 点击“下载 CSV”或“下载 XLSX”导出结果。筛选为空时的导出行为见下表。

计算过程中可点击“停止”立即终止当前任务，再修改条件重新计算。页面保留原有参数、按钮与规则说明；窄屏下输入区和结果区纵向排列，结果表可横向滚动查看全部八列。

HTTP 服务仅提供静态文件，计算由浏览器 CPU 执行。直接以 `file://` 打开 HTML 时，相邻工作簿的自动读取可能受到浏览器限制。

## 输入数据

网页读取 `食材`、`料理`、`稀客`、`食材merchant_data` 四张表。字段示例与完整导出结构见[输入输出说明](input-output.md)。随包数据文件为作者的完整原工作簿，其他工作表供 Python 分支或图像资料管理使用。

稀客类型字段应为 `rare` 或 `稀客`。重复基础食材以重复名称表示，例如 `豆腐、豆腐`。解析函数支持字段别名与列表分隔符，并排除食材“黑暗物质”“铃仙”及料理“黑暗物质”。网页不依据 `Owned` 筛选料理。

手动选取的文件在当前浏览器中读取，不上传至计算服务。网页使用已保存的单元格值，不执行工作簿公式重算；修改公式或其输入后，需要在支持相关公式的电子表格软件中重算并保存。来源与历史数据范围见[数据说明](data-provenance.md)。

## 标签计算与候选过滤

最终标签首先合并料理标签、厨具标签、售价派生标签与追加食材标签，再依次处理肉覆盖素、饱腹覆盖下酒、重油覆盖清淡、大份覆盖小巧，随后检测流行。基础食材消耗格数但不再次贡献标签；重复加料分别消耗格数，同名标签仅计一次。

网页得分为喜好命中数减去厌恶命中数，厌恶通过扣分进入评价。候选是否通过筛选还取决于得分阈值、必含／排除标签与下列过滤选项：

| 选项 | 作用 |
| --- | --- |
| 加料子集过滤 | 同一道料理中，依据已保留的加料子集筛除冗余候选；勾选“考虑得分”后，同时比较子集候选的得分 |
| 食材高级过滤 | 依据食材标签集合关系及对应候选进行过滤；“考虑得分”选项增加得分比较条件 |
| 等价食材去重（仅加料） | 按标签等价关系处理追加食材，不将基础配方食材视为等价替换对象 |
| 依采购推荐（按 TDQ） | 依据日供给量 `Total Daily Quantity` 比较采购可得性，结合 Top-N 设置保留推荐候选 |

“食材高级过滤”中的高级关系由标签集合确定，不直接等同于价格或稀有度。TDQ 比较不扣减每客订单需求。上述选项改变候选集合，其适用边界如下。

## 已知行为与限制

| 触发条件 | 实际行为 |
| --- | --- |
| 配方禁忌字段包含标签 | 禁忌仅匹配食材名称，标签型条目可能未限制加料 |
| TDQ 等价成员替换 | 替换可能重新引入此前禁用的食材 |
| 得分阈值设为 `0` | `Number(...) \|\| 3` 使阈值回退为 `3` |
| 售价为 `0` | 仍可能派生“实惠”标签 |
| 筛选结果为零行后导出 | 选取全部计算结果，再应用导出行数限制 |
| 重复等价加料与 Top-N | 权重按等价组大小连乘，重复组合计数可能影响推荐边界 |

这些行为构成当前查询与导出的使用边界，相关对照结果见[验证记录](verification.md)。

## 输出与图像

导出文件名为 `结果_<时间戳>.csv` 或 `结果_<时间戳>.xlsx`。XLSX 仅含 `结果` 工作表，两个格式均输出以下八列：

```text
售价,得分,料理,cookware,总食材数,基础食材,加料,最终tag
```

每行是一套候选料理与加料。筛选结果非空时，导出按结果区排序取行；筛选结果为空时，使用全部计算结果。导出限制为 `0` 时不限行数，正数限制导出的前若干行。该限制不减少候选枚举工作量，结果区最多显示 5,000 行，导出集合不受该显示上限约束。

稀客与料理图片通过 [名称映射](../HTML/icon_map.js) 从 [HTML/izakaya_icons_pack/](../HTML/izakaya_icons_pack/) 读取。58 张稀客头像和 163 张料理图片仅用于展示，不参与计算，也不嵌入导出的 CSV/XLSX 表格。`HTML/` 目录同时提供 SheetJS 和名称映射，因此须与 `index.html` 一同部署。

## 性能与模型范围

网页最多使用 8 个 CPU Web Worker，按料理静态分块。固定标签预编译为位集，组合通过约束与得分判断后再生成候选对象；搜索文本缓存减少重复查询的字符串构造。枚举顺序、候选过滤、排序与导出规则保持一致。食材数量、可追加槽位和过滤条件共同影响枚举规模；测量条件和结果见[验证记录](verification.md)，尚未建立跨设备性能基准。

查询针对单个稀客的标签与配方条件，不联合求解共享库存、完整满意度、酒水搭配或现金利润。Python PLAN 分支另定义喜好覆盖、食材件数与最低供给余量的评价目标；两类入口的候选处理与评价口径见[模型与算法](design.md)。
