# 网页使用说明

网页用于探索单个稀客的料理与加料方案，比较标签条件、加料数量和采购可得性。默认载入作者工作簿整理的**游戏数据快照**，可按名字搜索 58 位稀客。快照来自历史记录，不保证与游戏最新版本一致；来源及数量口径见[数据说明](data-provenance.md)。

## 开始使用

1. 保留完整仓库目录，在仓库根目录运行 `python -m http.server 8000 --bind 127.0.0.1`，访问 `http://127.0.0.1:8000`。游戏数据随页面加载；服务器只提供本地文件，不执行规划计算。
2. 选择稀客，设置得分阈值。必含、排除、流行附着标签可留空；多个标签用空格或顿号分隔。
3. 点击“开始计算”。结果显示售价、得分、基础食材、加料和最终标签；可搜索、排序，或按厨具、料理、得分和食材数筛选。
4. 点击“下载 CSV”或“下载 XLSX”导出**当前筛选结果**。筛选为空时不能导出。页面最多绘制前 5,000 行，导出可包含其余行；“导出限制”只限制导出行数。

“停止”会立即终止本次计算并清空未完成结果。修改参数后需要重新点击计算。通过文件选择器导入 `data/demo.json`，可复现合成案例；导入 `data/game.json` 可恢复游戏快照。页面本身也保留相应的数据载入按钮。

角色头像与料理图片通过 `web/icon-map.js` 按名称匹配 `web/icons/` 中的文件。58 位稀客和 163 道普通料理有对应图片；缺少映射或图片加载失败时，稀客用名字首字占位，料理仅显示名称。图片不参与标签、供给或方案计算。只复制 HTML 而漏掉 `web/` 目录，会丢失脚本、样式及图片依赖。

## 导入自己的数据

文件选择器支持原项目 XLSX，以及 `data/demo.json` 所用的 `mystia-planner-data/v1` JSON。两者经过相同的数据解析逻辑，文件只在当前浏览器中处理，不上传服务器。JSON 的 `sheets` 或 XLSX 工作表需要包含：

| 表 | 主要字段 |
| --- | --- |
| `食材` | `Name`、`Tags` |
| `料理` | `Name`、`Tags`、`Cookware`、`Sell Price`、`Required Ingredients`、`Forbidden Ingredients` |
| `稀客` | `Name`、`Type`（`rare` 或 `稀客`）、`Preferred Tags`、`Disliked Tags` |
| `食材merchant_data` | `Name`、`Total Daily Quantity` |

表头不区分大小写，并兼容代码中已有的中文别名。列表单元格可使用顿号、逗号、分号、斜杠、竖线、换行或制表符；JSON 也支持字符串数组。基础食材中重复的名字表示重复份数，必须保留，例如 `豆腐、豆腐` 占两个食材位置。普通空格不拆分文件中的名称，避免破坏带空格的名称。

禁忌项若能匹配食材名，按具体食材禁用；否则按食材标签禁用。禁忌只检查额外加料，包含该标签的加料即被排除。基础食材只占位置，不再次把自身标签叠加到料理上。

售价缺失时使用 `0` 表示未提供，不据此推导“实惠”。只有 `0 < 售价 < 20` 加“实惠”，`售价 > 60` 加“昂贵”；20 和 60 均不添加价格标签。负数及非有限数值会被拒绝。食材进货价在网页中不参与评分、排序或利润计算，缺失值不会形成“免费食材”的优化结论。

## 参数与筛选含义

| 参数 | 实际行为 |
| --- | --- |
| 得分阈值 | 最终标签与喜好交集的数量，减去与厌恶交集的数量；重复标签只计一次。阈值允许整数 −10 到 10。 |
| 必含 / 排除标签 | 必含项须全部满足；任一排除项出现便拒绝该方案。 |
| 流行附着标签 | 最终标签命中任一附着项时，添加对应流行标签；是否加减分仍由客人的喜好或厌恶决定。 |
| 加料子集过滤 | 同一道菜存在加料更少的子集方案时，移除冗余组合；勾选“考虑得分”后，只有子集得分不低于当前方案才移除。 |
| 食材高级过滤 | 按食材标签真子集关系寻找基础替代；对应替代方案存在时才过滤。这里“高级”表示标签集合关系，不表示价格、等级或稀有度。勾选“考虑得分”后还要求替代方案分数不低。 |
| 等价食材去重 | 额外加料的标签集合完全相同时合并搜索；基础配方不替换。无标签食材各自保留。 |
| 依采购推荐 | 对每道料理分别保留 TDQ 排名前 N 的方案及并列。TDQ 是每日采购量；同标签组使用已有 TDQ 的平均值，组合按最稀缺食材开始逐项比较，较大者优先。启用等价去重时，输出替换为该料理合法候选中 TDQ 较高的组成员。 |

加料允许重复，总食材数上限为 5。标签覆盖关系依次为：肉覆盖素、饱腹覆盖下酒、重油覆盖清淡、大份覆盖小巧。采购推荐属于可得性启发式，缺失 TDQ 按零处理；并列保留会使输出超过 N 条。

## 网页与 Python 规划器的区别

两个入口保留了项目不同阶段的用途，输出不应直接混作同一种“最优解”。

| 方面 | 网页 | Python 规划器 |
| --- | --- | --- |
| 分析目标 | 单个稀客的多种可行加料方案，交互筛选比较 | 多个稀客共享限定种类厨具时的方案选择 |
| 厌恶标签 | 净分扣分；净分足够时仍可能保留 | 最终标签命中任何厌恶项即硬排除 |
| 持有状态 | 读入后不作为筛选约束 | 使用持有的料理；数据无持有列时按可用处理 |
| 采购考量 | TDQ 向量排序，不扣减需求 | 根据每日单量与重复食材份数计算供给余量，用于排序 |
| 厨具 | 对完成后的结果做筛选 | 在允许的厨具集合中选择指定数量 |

两端都不模拟完整满意度、酒水搭配、客人预算约束、实际利润或跨客人共享库存。Python 的供给余量也允许负数，并不保证供应可行。更完整的目标与取舍见 [设计说明](design.md)。

## 规模与验证边界

网页使用最多 8 个 CPU Web Worker，未使用 GPU。候选数会随可用食材和加料槽位快速增长；完整游戏数据可能耗时且占用较多内存。先开启等价食材去重、提高阈值或增加必含标签，有助于缩小结果范围。导出行数限制不能降低枚举工作量。

发布包包含针对真实 Worker 与导入函数的自动回归测试：`node --test tests/web-regression.cjs`。这些测试验证软件规则与已修复的边界，不替代游戏内对照实验。使用真实数据时还需确认数据版本、来源与机制假设。
