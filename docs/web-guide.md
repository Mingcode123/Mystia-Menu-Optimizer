# 网页使用说明

网页保留原版单客料理查询界面与计算逻辑。默认从同目录的 `东方夜雀食堂.xlsx` 读取游戏数据，使用独立的名称映射显示稀客头像与料理图片。工作簿来自历史记录，具体游戏版本和采样日期未完整留存。

## 开始使用

1. 保留完整仓库目录，在根目录运行 `python -m http.server 8000 --bind 127.0.0.1`，访问 `http://127.0.0.1:8000`。
2. 页面会自动请求默认 Excel；也可以通过原文件选择器导入 XLSX。当前网页不接受 JSON 文件。
3. 选择稀客，设置得分阈值、必含／排除标签及流行锚点，点击“开始计算”。
4. 查看候选的料理、厨具、基础食材、加料、得分和最终标签，使用原筛选与排序控件比较结果。
5. 使用“下载 CSV”或“下载 XLSX”导出。原导出在筛选为空时会回退到全部结果，导出前应核对表格和筛选状态。

本地 HTTP 只提供文件，计算由浏览器 CPU 执行。直接双击 HTML 时，浏览器可能限制自动读取相邻工作簿；本说明以 HTTP 路径为运行方式。

## 输入数据

网页读取四张表：`食材`、`料理`、`稀客`、`食材merchant_data`。根工作簿还包含其他原 Python 分支使用的表，不影响网页按原规则读取。

| 表 | 字段示例 |
| --- | --- |
| `食材` | `Name`、`Tags` |
| `料理` | `Name`、`Tags`、`Cookware`、`Sell Price`、`Required Ingredients`、`Forbidden Ingredients` |
| `稀客` | `Name`、`Type`、`Preferred Tags`、`Disliked Tags` |
| `食材merchant_data` | `Name`、`Total Daily Quantity` |

稀客类型应为 `rare` 或 `稀客`。原程序保留自己的别名与列表分隔解析；重复基础食材用重复名称记录，例如 `豆腐、豆腐`。原解析跳过食材“黑暗物质”“铃仙”及料理“黑暗物质”。网页不使用 Python 的持有状态筛选规则。

用户文件只在当前浏览器读取。价格、供给和标签按原程序解释，使用已保存的缓存值。工作簿角色和导出字段见[输入输出说明](input-output.md)。

## 标签与筛选

最终标签由料理、厨具、售价派生和加料合并，再处理肉覆盖素、饱腹覆盖下酒、重油覆盖清淡、大份覆盖小巧，随后检测流行。基础食材占格但不再次贡献标签；重复加料占格，标签只计一次。

网页得分为喜好命中数减厌恶命中数，不将所有厌恶作为硬排除。加料子集过滤、食材高级过滤、等价去重和采购推荐均沿用原实现；“高级”涉及标签集合关系，不是按价格或稀有度直接删食材。TDQ 用于采购可得性比较，不扣减每客订单需求。

这些选项会影响保留的候选。它们具有以下已识别边界，不应当作对任意数据均保留最优方案的保证。

## 原版已知行为

| 情况 | 保留的实际行为 |
| --- | --- |
| 配方禁忌写成标签 | 禁忌仅匹配食材名称，标签型条目可能未限制加料 |
| TDQ 等价成员替换 | 替换可能重新引入此前禁用的食材 |
| 得分阈值设为 0 | `Number(...) || 3` 使其回退为 3 |
| 售价为 0 | 仍可能派生“实惠”标签 |
| 点击停止 | 向 Worker 发送 STOP；同步枚举忙碌时不保证立即响应 |
| 筛选后零行再导出 | 回退到全部计算结果，不是导出空表 |
| 重复等价加料与 Top-N | 权重沿用组大小连乘方式，重复组合计数可能影响推荐边界 |

本版没有以包装整理为由修正这些行为。对原程序和发布副本的对照方法见[验证记录](verification.md)。

## 输出与图片

导出文件名为 `结果_<时间戳>.csv` 或 `.xlsx`，XLSX 只有 `结果` 工作表，列为：

```text
售价,得分,料理,cookware,总食材数,基础食材,加料,最终tag
```

导出保留原排序及行数限制处理。它是候选结果，不能重新当成四表源工作簿。页面最多显示的行数与实际导出行数由原显示及导出逻辑分别处理。

稀客与料理图片按 [名称映射](../HTML/icon_map.js) 从 [HTML/izakaya_icons_pack/](../HTML/izakaya_icons_pack/) 读取。58 张稀客头像和 163 张料理图片只用于显示，不参与计算或嵌入上述候选导出。缺图回退沿用原程序。`index.html` 内嵌原样式和计算脚本，旁边的 `HTML/` 目录仍需保留，以提供 SheetJS、名称映射和图片。

## 性能与适用范围

网页最多使用 8 个 CPU Web Worker，按料理静态分块。加料槽位、食材数量和过滤条件会影响枚举规模；导出行数限制不减少枚举工作量。没有跨设备性能基准，也没有全游戏机制准确性保证。

网页不联合优化共享库存、完整满意度、酒水和现金利润。Python PLAN 分支有独立的余量目标与候选处理，不能将两者的结果混作同一个最优解。详细模型见[设计说明](design.md)。
