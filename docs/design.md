# 数学目标与原实现

本页区分模型希望比较的量、各原始脚本的决策单位，以及实现实际生成的候选范围。不同分支不能仅因共享部分函数就视为相同程序。

<a id="数学建模从历史多方案到当前单方案"></a>

## 1. 从标签方案到顾客方案

| 原脚本 | 决策单位 | 比较目标 |
| --- | --- | --- |
| `detailedPLAN.py` | 每个可覆盖喜好标签一套方案 | 最少预期食材件数，其次最大最低供给余量 |
| `singlePLAN.py` | 每客一套方案 | 最大喜好覆盖，其次最少件数、最大余量 |
| `singlePLAN_cover3.py` 及后续混排分支 | 每客一套方案 | 喜好收益封顶三，再比较件数和余量 |
| `limitedCookware` 分支 | 源码排除列表下的逐客方案 | 封顶单客目标 |
| `nCookware` 分支 | 恰好 n 种共同厨具下的逐客方案 | 汇总覆盖、件数和逐客余量，含无解惩罚 |

`mixedingredients` 主要改变 Excel 中基础与追加食材的排布，不应当作新的效用函数。预算用于展示。独立利润脚本采用价格字段做分析，不是 PLAN 系列的目标。

## 2. 标签、用量与约束

设方案 $`p=(d,x)`$ 由基础料理 $`d`$ 和非负整数加料向量 $`x`$ 组成。基础用量为 $`b_i(d)`$，总用量为：

```math
c_i(p)=b_i(d)+x_i,\qquad x_i\in\mathbb Z_{\ge0},\qquad
L(p)=\sum_i c_i(p)
```

五格限制对应设计约束 $`L(p)\le5`$。基础食材计入用量但不再次贡献标签；追加食材标签按集合合并。随后处理肉覆盖素、饱腹覆盖下酒、重油覆盖清淡、大份覆盖小巧，再根据最终标签触发流行。

这些规则由各入口自己的代码执行。原 Python 按名称和标签拆分配方禁忌，原网页禁忌只匹配食材名称；原网页零售价也会得到“实惠”。输入异常、字段缺失和零阈值等边界不得只依据设计公式推定为已正确处理。

流行喜爱与厌恶由各自的标签锚点触发。`nCookware` 在某方向没有锚点时，还会从顾客偏好与厌恶中移除该方向的流行标签。其最终候选排除厌恶命中，默认喜好门槛为三。

## 3. 历史多方案模型

假设每日订单量 $`K`$ 在 $`m>0`$ 个有候选的标签方案之间均分。若 $`u_i`$ 是各方案中食材 $`i`$ 的累计用量，$`q_i`$ 是日供给估计：

```math
E_{\mathrm{old}}=\frac{K}{m}\sum_i u_i,\qquad
R_{\mathrm{old}}=\min_{i:u_i>0}\left(q_i-\frac{K}{m}u_i\right)
```

先最小化 $`E_{\mathrm{old}}`$，再在第一目标并列的组合中最大化 $`R_{\mathrm{old}}`$。原按标签实现保留各标签的并列最少件数候选，第二阶段再组合比较。没有可行标签时没有方案；均分订单不是实测标签订单概率。

第二阶段可询问：是否存在候选组合，使所有实际使用食材满足：

```math
q_i-\frac{K}{m}u_i\ge\lambda
```

较高 $`\lambda`$ 可行，较低门槛也可行，由此可以二分门槛。内部仍需组合可行性搜索，原分支使用 DFS、容量剪枝和状态缓存；不能将整个算法的复杂度直接说成对数级。`nCookware` 文件留存部分历史函数，不表示其正常主流程仍调用这套多方案求解。

## 4. 单客模型

设 $`h_g(p)`$ 是方案对顾客 $`g`$ 的喜好命中数。该客所有假设订单使用同一方案，因此：

```math
R(p)=\min_{i:c_i(p)>0}\left(q_i-Kc_i(p)\right)
```

`singlePLAN.py` 首先比较未封顶覆盖。cover3 及后续分支使用 $`U(h)=\min(h,3)`$：第四项喜好的目标边际收益为零。对原程序生成并保留的候选集 $`\mathcal C_g`$，核心比较为：

```math
\max_{p\in\mathcal C_g}^{\mathrm{lex}}
\left(U(h_g(p)),\;-L(p),\;R(p)\right)
```

词典序没有指标间的加权补偿。三项完全相同时，原代码依次采用较高售价、料理名和原加料字符串作确定性平局处理。默认 $`K=5`$，最低分为三；改变最低分不改变 cover3 的收益上限。

供给余量可以为负，它是方案比较指标而不是库存硬约束。计算没有扣减其他顾客的消耗，汇总逐客余量也不等于共同库存剩余量。

## 5. 厨具配置

在 `nCookware` 中，$`H`$ 是已拥有料理对应的可用厨具集合，枚举 $`S\subseteq H,\;|S|=n`$。每客每厨具候选预先计算一次；对于集合 $`S`$，各客从允许厨具的结果中选择原比较规则下的最佳候选。

设有方案顾客集合为 $`G_S`$，无解人数为 $`z_S`$，程序的三项集合比较值为：

```math
\left(
\sum_{g\in G_S}U(h_g(p_g)),\;
-\left[\sum_{g\in G_S}L(p_g)+10^9 z_S\right],\;
\sum_{g\in G_S}R(p_g)-10^{18}z_S
\right)
```

默认三分门槛下，每个有解顾客覆盖收益都是三，因此首项推动有解人数增加；降低门槛后不能将覆盖总量直接等同于人数。厨具数量是恰好 n 种，平局集合可能含最终料理未用到的设备。

`limitedCookware` 的排除列表是另一独立分支的源码配置，不能写成 `nCookware` 已提供额外的命令行排除参数。

## 6. 原候选范围与最优性边界

原 Python 候选生成包含相关加料筛选、标签等价代表选择、DFS 上界及中性补位截断。等价组最终偏好原始 TDQ 较高的合法成员；用于凑“大份”的中性补位最多保留前三项。这些处理影响 $`\mathcal C_g`$，因此目标函数定义本身不构成全部合法具体食材组合上的最优性证明。

一个说明组内分配差异的算例：A、B 标签相同，日供给分别为 10、9；基础配方已用 A，另需追加同类标签，$`K=5`$。若继续加 A，最低余量为 $`10-5\times2=0`$；若追加 B，最低余量为 $`\min(10-5,9-5)=4`$。原始 TDQ 的代表排序可能偏向 A，但计入基础耗用后的余量更优组合是 A+B。此例说明模型目标与代表选择的局部规则不能混同。

当前发布保留原选择方式，没有引入新的组内容量分配算法，也没有取消中性前三截断。网页还有标签型禁忌、零阈值、等价替换和停止等已知边界，详见[网页指南](web-guide.md)。

## 7. 评价程序结果的方法

先固定入口版本、工作簿、流行条件、最低分、订单数及厨具回答，再比较候选、目标值和输出格式。跨分支目标变化可以合理改变结果；同一原程序的发布副本则应以相同输入核对行为。
