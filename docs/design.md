# 优化模型与算法边界

本章定义料理规划中的决策变量、评价指标与比较顺序，并说明各脚本的候选生成范围。模型分为按喜好标签配置多个方案、按顾客配置单个方案，以及选择共同厨具集合三个层次。各层次具有不同的决策单位与目标函数。

[README 第一章](../README.md#zh-model)以双语总览图展示从网页候选筛选到各规划模型的变化。本章提供数学细节；图中的顺序表示决策依赖，不代表 HTML 调用 Python 或精确开发日期。

## 1. 模型分支与决策单位

| 脚本或分支 | 决策单位 | 目标顺序 |
| --- | --- | --- |
| `index.html` | 对指定顾客枚举并筛选多个料理与加料候选 | 净分门槛与可选过滤；采购推荐在每道料理内部按供给向量排序，没有统一的跨料理最优目标 |
| `detailedPLAN.py` | 每个可覆盖喜好标签对应一套方案 | 最小预期食材件数，其次最大最低供给余量 |
| `singlePLAN.py` | 每位顾客对应一套方案 | 最大喜好覆盖，其次最小食材件数、最大最低供给余量 |
| `singlePLAN_cover3.py` 及后续混排分支 | 每位顾客对应一套方案 | 喜好覆盖收益封顶为 3，其次最小食材件数、最大最低供给余量 |
| `limitedCookware` 分支 | 指定厨具排除列表下的逐客方案 | 覆盖封顶后的单客目标 |
| `nCookware` 分支 | 恰好 n 种共同厨具下的逐客方案 | 汇总覆盖收益、食材件数与逐客最低供给余量，并计入无解惩罚 |

`mixedingredients` 分支将基础食材与追加食材合并到五个 Excel 输出格，沿用覆盖封顶目标。顾客预算为展示字段；普客、酒水、价格与利润分析由独立脚本提供，未纳入 PLAN 系列的联合目标。

## 2. 决策变量与制作约束

设料理方案 $`p=(d,x)`$ 由基础料理 $`d`$ 与非负整数加料向量 $`x`$ 构成。$`b_i(d)`$ 表示基础配方中食材 $`i`$ 的用量，$`c_i(p)`$ 表示其总用量，$`L(p)`$ 为总食材件数：

```math
c_i(p)=b_i(d)+x_i,\qquad x_i\in\mathbb Z_{\ge0},\qquad
L(p)=\sum_i c_i(p)
```

五格制作限制对应 $`L(p)\le5`$。基础食材参与用量与格数计算，料理标签以工作簿记录为准；追加食材的标签按集合合并。因此，同一种食材重复加入会增加件数，相同标签仅计一次。

标签处理包含肉覆盖素、饱腹覆盖下酒、重油覆盖清淡、大份覆盖小巧，随后依据处理后的标签判断流行状态。流行喜爱与流行厌恶分别由指定标签触发。`nCookware` 在某方向未指定触发标签时，从顾客偏好与厌恶中移除该方向的流行标签；最终候选排除厌恶命中，默认喜好门槛为 3。

制作规则由各入口分别实现。Python 将配方禁忌分为名称型与标签型条件，网页实现仅匹配食材名称；网页采用喜好命中数减厌恶命中数的净分。具体解析条件与参数行为见[输入输出说明](input-output.md)及[网页使用说明](web-guide.md)。

## 3. 按标签配置的多方案模型

对每个具有可行候选的喜好标签 $`t`$，在包含该标签且通过准入的子池中执行原食材升级与追加子集过滤，从保留候选中选择方案 $`p_t`$。假设每日订单量 $`K`$ 在 $`m>0`$ 个标签之间均分；同一料理方案可承担多个标签份额。令 $`u_i=\sum_t c_i(p_t)`$ 为所选方案中食材 $`i`$ 的累计用量，$`q_i`$ 为日供给估计，定义预期食材件数与最低供给余量：

```math
E_{\mathrm{old}}=\frac{K}{m}\sum_i u_i,\qquad
R_{\mathrm{old}}=\min_{i:u_i>0}\left(q_i-\frac{K}{m}u_i\right)
```

目标首先最小化 $`E_{\mathrm{old}}`$，随后在第一目标并列的组合中最大化 $`R_{\mathrm{old}}`$，即按词典序最小化 $`(E_{\mathrm{old}},-R_{\mathrm{old}})`$。固定标签数时第一目标可按标签分解，因此对应实现先保留各标签全部并列最少件数候选，再比较组合的最低供给余量；余量最小时仍并列则比较完整的升序余量向量。$`m`$ 仅统计具有可行候选的标签，不是不同料理的数量；无可行标签时无方案输出。订单均分属于模型假设，缺少实测标签订单概率的支持。

第二阶段将最低供给余量的最大化转化为给定阈值 $`\lambda`$ 的可行性判定，即寻找满足下式的候选组合：

```math
q_i-\frac{K}{m}u_i\ge\lambda
```

该条件适用于组合中实际使用的每种食材。可行性随阈值降低单调放宽，因此外层采用二分搜索；内层采用 DFS、容量剪枝与状态缓存进行组合判定。整体计算量同时取决于阈值搜索次数与单次可行性搜索的规模。

上述方法对应历史多标签分支。`nCookware` 文件中的部分历史函数未被其正常主流程调用，执行路径见[架构说明](architecture.md)。

## 4. 按顾客配置的单方案模型

设 $`h_g(p)`$ 为方案 $`p`$ 对顾客 $`g`$ 的喜好命中数。该顾客的全部假设订单采用同一方案，最低供给余量为：

```math
R(p)=\min_{i:c_i(p)>0}\left(q_i-Kc_i(p)\right)
```

`singlePLAN.py` 按词典序最大化 $`(h_g(p),-L(p),R(p))`$：决策由多个标签方案改为每客一个方案，全部假设订单使用该方案，不再按标签均分。cover3 及后续分支采用 $`U(h)=\min(h,3)`$，覆盖第 4 项喜好的目标边际收益为零。对于实现生成并保留的候选集 $`\mathcal C_g`$，核心目标为：

```math
\max_{p\in\mathcal C_g}^{\mathrm{lex}}
\left(U(h_g(p)),\;-L(p),\;R(p)\right)
```

词典序比较仅在前一指标相同时比较后一指标。较高的最低供给余量不能补偿较多的食材件数。三项目标均相同时，程序依次按较高售价、料理名与加料字符串处理平局。

默认订单量为 $`K=5`$，最低分为 3。最低分控制候选准入，覆盖上限控制目标收益；修改最低分不改变 cover3 的收益上限。最低供给余量允许为负，属于方案排序指标。各顾客的食材需求独立核算，未共同扣减共享库存。

封顶只影响目标收益，不截断原始得分或最终标签。例如，博丽灵梦的饭团加蜂蜜在无流行时为 3 项喜爱、0 项厌恶；当「甜」触发流行喜爱时，原「甜」保留，并新增「流行·喜爱」，原始得分为 4。两种条件下覆盖效用均为 3，总用料均为 2 件。该例已使用原工作簿和原候选函数核对，见[验证记录](verification.md#流行条件与封顶效用对照)。

## 5. 共同厨具配置模型

`nCookware` 以已拥有料理对应的厨具构成可用集合 $`H`$，枚举 $`S\subseteq H,\;|S|=n`$。每客每厨具的候选预先计算一次。对于给定集合 $`S`$，每位顾客从允许厨具的结果中按单客比较规则选择最佳候选。

设 $`G_S`$ 为存在方案的顾客集合，$`z_S`$ 为无解顾客数，集合层面按以下三项进行词典序比较：

```math
\left(
\sum_{g\in G_S}U(h_g(p_g)),\;
-\left[\sum_{g\in G_S}L(p_g)+10^9 z_S\right],\;
\sum_{g\in G_S}R(p_g)-10^{18}z_S
\right)
```

在默认最低分为 3 的条件下，有解顾客的覆盖收益均为 3，首项目标等价于优先增加有解顾客数。降低门槛后，各顾客覆盖收益可能不同，应按覆盖收益总和解释。厨具集合的大小恰好为 n，平局集合可能包含最终料理未使用的设备。

`limitedCookware` 通过源码中的排除列表限制设备，`nCookware` 通过交互输入指定数量，两者为独立配置方式。其集合目标汇总逐客最低供给余量，未建立多顾客联合库存约束。

## 6. 候选生成与最优性范围

Python 候选生成采用相关加料筛选、标签等价代表选择、DFS 得分上界与中性补位截断。等价组优先选择原始日供给量 TDQ 较高的合法成员；用于凑足“大份”的中性补位最多保留前三项。上述处理共同决定 $`\mathcal C_g`$ 的范围。

标签等价仅描述标签集合相同。供给量及基础配方耗用不同的食材，在资源目标下仍可能具有不同效果。考虑以下反例：食材 A、B 标签相同，日供给分别为 10、9；基础配方已使用 1 份 A，还需追加 1 份同类标签食材，订单量为 $`K=5`$。

| 追加选择 | 总用量 | 最低供给余量 |
| --- | --- | --- |
| A | A 共 2 份 | $`10-5\times2=0`$ |
| B | A、B 各 1 份 | $`\min(10-5,9-5)=4`$ |

按原始 TDQ 选择代表可能优先追加 A，而计入基础耗用后，A+B 的最低供给余量更高。该反例说明，仅依据原始供给排序选择等价代表不足以完成组内资源分配优化。

本项目的最优性表述限定于所实现的候选生成与比较过程。完整合法具体食材组合的全局最优性尚未建立。网页中的标签型禁忌、零阈值、等价替换与停止响应等边界另见[网页使用说明](web-guide.md)。

## 7. 结果评价与验证范围

结果比较应固定脚本版本、工作簿、流行条件、最低分、订单量与厨具配置，并同时记录候选、目标值和输出格式。目标或约束改变时，最佳方案可能随之变化；求解加速与排版调整则以相同输入下的目标值和输出约定为验收依据。若存在并列候选，具体方案的一致性还取决于平局规则。

已完成的源码与小规模运行对照见[验证记录](verification.md)。现有证据覆盖指定文件及测试条件；完整游戏评价、真实订单概率、多顾客共享库存、现金利润与跨设备性能尚不在验证范围内。

## 8. 网页候选与采购排序

网页针对指定顾客返回候选集合，其净分为喜好命中数减厌恶命中数。达到净分门槛并通过必含、排除等可选过滤即可保留；它没有采用 PLAN 的“任何厌恶命中都排除”条件。网页的配方禁忌仅按食材名称匹配，读取的持有字段未用于枚举过滤，具体行为见[网页指南](web-guide.md)。

采购推荐仅在每道料理内部排序。设同标签食材组为 $`G(i)`$，其中有已知日供给量的成员为 $`M(i)`$；组内供给均值为：

```math
\widetilde q_i=\frac{1}{|M(i)|}\sum_{j\in M(i)}q_j
```

当没有可用组均值时，代码回退到该食材的已知供给或 0。对基础配方与追加食材的每一件分别放入其组均值，形成升序向量：

```math
v(p)=\mathrm{sort}_{\uparrow}
\left(\underbrace{\widetilde q_i,\ldots,\widetilde q_i}_{c_i(p)\ \mathrm{times}}\right)_i
```

实现按该向量做字典序降序比较，较短向量的缺失位置按正无穷处理；在每道料理内取指定名次的向量作为阈值，并保留并列。启用等价去重时，累计排名使用原代码的代表方案权重，不将该权重宣称为重复加料情况下无重复组合的精确计数。输出时，追加食材还会替换为同标签组内实际 TDQ 最高的成员。

该向量使用供给规模，没有扣除假设日需求。因此，网页采购排序与 Python 的最低供给余量是两种不同指标；网页也没有把不同料理一起求解成一个最优方案。
