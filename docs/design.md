# 从备菜问题到规则与决策工具

这个项目源于《东方夜雀食堂》的实际游玩：面对不同顾客，怎样在明确的目标与约束下找到最优料理方案？我把这个问题拆成可配置的规则、明确的比较指标和可执行的搜索；需求变化时重新定义最优，模型固定时要求提高求解速度并保持结果含义。

项目包括单客候选查询和批量菜单规划两条路径。网页便于调整条件、比较料理与加料；Python 便于为多位顾客生成方案并比较厨具组合。它们读取相同类型的数据，但并非同一个算法的两个界面。

## 把游戏机制转成可计算规则

一份方案由基础料理和追加食材组成。基础配方消耗食材，但不把基础食材标签再次叠加到料理；追加食材才贡献加料标签。重复加同一种食材会重复消耗，重复标签仍只计一次。

候选标签经过厨具、售价标签、标签覆盖和流行状态处理，再与顾客喜好比较。例如“肉”覆盖“素”，“饱腹”覆盖“下酒”，“重油”覆盖“清淡”，“大份”覆盖“小巧”。这使结果不能只靠累加所有原始标签来判断。

| 决策条件 | 模型中的处理 | 设计目的 |
| --- | --- | --- |
| 基础配方与加料 | 总食材件数最多为 5；配方禁忌限制追加食材，需区分名称与标签 | 保证方案能在所建模的制作规则下成立 |
| 顾客喜好与厌恶 | 网页显示喜好命中减厌恶命中的标签分；批量规划进一步排除最终命中厌恶的方案 | 将探索性比较和保守推荐区分开 |
| 厨具 | 排除指定厨具，或限定可选厨具数量 | 把菜单选择与实际可用设备联系起来 |
| 日供给 | 使用输入表中的每日供给值比较方案余量 | 避免在其他指标相同时持续选择供应紧张的食材 |
| 顾客预算 | 保留作展示信息，不作为当前求解约束 | 明确当前模型覆盖的范围 |

这些是项目采用的规则模型。标签分不是完整的游戏评价公式，供给估计也不是当前背包库存；本项目没有把所有游戏机制或版本差异纳入求解。

## 为什么把喜好覆盖收益封顶为三个

早期单方案设计希望尽可能覆盖顾客喜好，但更高覆盖可能需要更多食材。后来我将目标改成“达到三个即可”，使方案在满足门槛后优先减少食材件数。

单客批量方案按以下顺序比较，而不是把所有指标加成一个难以解释的总分：

1. 优先提高喜好覆盖，收益计算为 `min(命中喜好数, 3)`。
2. 覆盖相同时，优先减少基础配方与加料的总件数。
3. 件数相同时，优先提高所用食材中的最低日供给余量。
4. 仍相同时，用售价、名称等固定次序处理平局，便于复现。

默认合格门槛同样为 3，且批量规划排除厌恶，因此默认条件下，合格方案的封顶覆盖都相同。此时厨具组合比较的主要意义是让更多顾客有合格方案，再减少食材件数、改善余量。这里的“件数少”不等于“采购金额低”，较高售价的平局规则也不等于利润优化。

单客方案的供给余量记为：

```text
supply_margin = min(q_i - K × c_i)，i 仅遍历该方案使用的食材
```

`q_i` 是食材的输入日供给，`K` 是假设日订单数，`c_i` 是一份方案的食材用量。它用于比较同一订单假设下的供给压力，可以为负。不同顾客的消耗没有在这个指标中共同扣减，因此它不是整晚联合库存保障，也不保证推荐菜单不会缺货。价格期望的含义另见[数据来源与估计方法](data-provenance.md)。

## 数学建模：从历史多方案到当前单方案

下面把历史需求和代码中的比较规则整理为数学表达，不是当时 prompt 的逐字引用。历史模型说明当时的取舍；当前模型对应公开包的 Python 实现。网页的净分筛选与 TDQ 排序另见[架构说明](architecture.md#网页与-python-的结果为何不同)。

### 历史模型：先锁定件数，再改善供给

对一位顾客，令 $`\mathcal T`$ 为有可行候选、参与第二阶段的喜好标签集合，$`m=|\mathcal T|>0`$。$`\mathcal A_t`$ 是命中标签 $`t`$、满足评分和制作规则，并经过旧版过滤后保留的候选集。每份方案 $`p`$ 的食材用量为 $`c_i(p)`$，其中包括基础配方和加料；总件数为 $`L(p)=\sum_i c_i(p)`$。

第一阶段为每个标签求最少件数，并保留全部并列候选：

```math
\ell_t^*=\min_{p\in\mathcal A_t}L(p),\qquad
\mathcal A_t^*=\{p\in\mathcal A_t:L(p)=\ell_t^*\}
```

第二阶段从每个 $`\mathcal A_t^*`$ 中选一个方案 $`p_t`$。设该顾客的假设日订单数为 $`K>0`$，订单均分到这 $`m`$ 个标签，则：

```math
u_i=\sum_{t\in\mathcal T}c_i(p_t),\qquad
E_{\mathrm{old}}=\frac Km\sum_i u_i
=\frac Km\sum_{t\in\mathcal T}\ell_t^*
```

第一阶段已固定最少预期食材件数，第二阶段只在这些候选之间改善最低供给余量：

```math
\max_{p_t\in\mathcal A_t^*\;(t\in\mathcal T)}
R_{\mathrm{old}},\qquad
R_{\mathrm{old}}=\min_{i:u_i>0}\left(q_i-\frac Km u_i\right)
```

这解释了为什么第一阶段必须保留并列方案：它们用量相同，却可能消耗不同的食材，留下的供给余量也不同。同一份料理可以服务多个标签，仍按各标签的订单份额累计；$`m`$ 不是不同菜名的数量。

**λ 可行性判定。** 不直接比较所有组合的余量，而先提出门槛 $`\lambda`$，检查能否为每个标签选出方案、使所有实际使用食材的余量都达到它：

```math
R_{\mathrm{old}}\ge\lambda
\quad\Longleftrightarrow\quad
u_i\le\left\lfloor\frac{q_i-\lambda}{K/m}\right\rfloor
\quad\text{for every }i\text{ with }u_i>0
```

例如 $`K=6,m=3,q_i=10`$，若要求 $`\lambda=4`$，食材 $`i`$ 在三份标签方案中的累计用量最多为 $`\lfloor(10-4)/2\rfloor=3`$。门槛提高到 6，就最多只能用 2 份。它把“供给更宽裕”变成了一个可检查的容量条件。

门槛越高，可行选择越少；较高 $`\lambda`$ 可行，所有更低门槛也可行。旧实现用 DFS 检查组合是否满足容量，并在 $`q_i-(K/m)u`$ 形成的离散门槛中二分；每份方案最多五件，所以枚举的累计用量范围可界定为 $`0\le u\le5m`$。这段说明解释建模与求解思路，不替代对旧实现的正确性验证。

这个历史模型有明确假设：旧代码剔除无候选标签后，将全部 $`K`$ 份订单重新均分给剩余标签，因此没有估计未覆盖标签的订单损失。均分不是实测概率；优化范围也是旧过滤流程保留的候选，不能推导成完整游戏的全局最优。

### 当前模型：整数加料与词典序目标

决策单位改为每顾客一套后，令 $`p=(d,\mathbf x)`$ 表示基础料理 $`d`$ 与追加食材向量。$`b_i(d)`$ 是基础配方中食材 $`i`$ 的份数，$`x_i`$ 是追加份数，$`\mathcal I_d`$ 是该料理的合法加料集合：

```math
x_i\in\mathbb Z_{\ge0},\qquad
x_i=0\;(i\notin\mathcal I_d),\qquad
c_i(p)=b_i(d)+x_i,\qquad
L(p)=\sum_i c_i(p)\le5
```

整数变量允许同种食材重复加入。禁忌限制的是 $`x_i`$，不把基础配方的 $`b_i(d)`$ 删掉。基础食材参与用量，却不额外贡献标签。

令 $`T(p)`$ 为按料理、厨具、售价、加料、覆盖与流行顺序处理后的最终标签集，$`P_g,D_g`$ 为当前流行状态下顾客的有效喜好与厌恶集合。定义命中数与标签分：

```math
h_g(p)=|T(p)\cap P_g|,\qquad
s_g(p)=h_g(p)-|T(p)\cap D_g|
```

Python 的可行候选还要求已拥有料理、厨具可用，以及：

```math
T(p)\cap D_g=\varnothing,\qquad s_g(p)\ge\tau
```

$`\tau`$ 为最低标签分，默认 3。对可行集 $`\mathcal F_g`$，使用封顶收益 $`U_g(p)`$ 和最低供给余量 $`R(p)`$：

```math
U_g(p)=\min(h_g(p),3),\qquad
R(p)=\min_{i:c_i(p)>0}\bigl(q_i-Kc_i(p)\bigr)
```

```math
\max_{p\in\mathcal{F}_g}^{\mathrm{lex}}
\bigl(U_g(p),-L(p),R(p)\bigr)
```

词典序表示先比较覆盖收益，只有相等才比较件数，再相等才比较余量。三项全相同时，当前代码按售价降序、料理名升序、排序后的加料名升序确定结果。实现位置为 [`Candidate.preference_key`](../src/mystia_planner/models.py)。

覆盖封顶的设计含义是 $`U(4)-U(3)=0`$：第四个喜好不再增加目标收益。如果它需要更多食材，该方案就会输在第二项。最低分 $`\tau`$ 仍独立约束可行性；例如 $`\tau=4`$ 必须先达到四分，不能因为收益封顶为 3 就只要求三分。

从多方案切换为单方案后，同一份料理承接该顾客全部假设订单，所以消耗项由 $`(K/m)u_i`$ 改为 $`Kc_i(p)`$。两处的用量变量含义不同，不能只把分母删掉而继续累加多个标签方案。

### 厨具约束：比较同一设备集合下的逐客结果

令 $`H`$ 为排除指定项后的可用厨具集合，选择 $`S\subseteq H`$ 且 $`|S|=n`$。$`G`$ 是本次参与规划的顾客集合；对每位顾客，在使用 $`S`$ 的候选中按上述词典序选一份。令 $`G_S`$ 为有方案的顾客集合，$`\nu(S)=|G|-|G_S|`$ 为无方案人数。

当前代码比较厨具组合时使用：

```math
\max_{S\subseteq H,\;|S|=n}^{\mathrm{lex}}
\left(
\sum_{g\in G_S}U_g,\;
-\sum_{g\in G_S}L_g-10^9\nu(S),\;
\sum_{g\in G_S}R_g-10^{18}\nu(S)
\right)
```

这里的 $`U_g,L_g,R_g`$ 指该集合下选出的逐客方案指标；平局再按规范化厨具名称排列。两个缺解惩罚仅用于比较，不是真实食材消耗。对应代码为 [`plan_dataset()`](../src/mystia_planner/planner.py)，输出将真实合计与带惩罚的比较值分开。

默认 $`\tau=3`$ 时，所有合格方案的 $`U_g=3`$，因此第一项等于 $`3|G_S|`$，优先让更多顾客有方案；$`\tau=1`$ 或 2 时，不再等价于人数最多。选择恰好 $`n`$ 件厨具，也不要求最终菜品把每件都用上。

**数学模型的边界。** 以上供给最小值只考察实际使用的食材，允许为负，没有加入 $`Kc_i\le q_i`$ 的库存硬约束。厨具目标汇总的是各客单独算出的余量，没有共同扣减食材；$`L`$ 的单位是件数，不是金额。这些公式不包含酒水、完整满意度、利润或预算约束。

## 需求怎样演进

| 阶段 | 改变的决策问题 | 复盘 |
| --- | --- | --- |
| 标签查询与加料枚举 | 给定顾客与目标标签，查找达到门槛的料理组合；早期还提出按实际利润排列 | 明确制作规则；早期利润排序意图不等于当前实现了利润优化 |
| 候选筛选 | 在大量可行结果中减少冗余，并讨论何时可以用替代食材 | “标签相同”不一定意味着供给表现相同，简化需要反例检查 |
| 每标签一套方案 | 结合各类订单选择多套方案，兼顾预期食材消耗与供给余量 | 需要显式说明订单在标签之间如何分配 |
| 每顾客一套方案 | 为每客选一份方案，覆盖数优先，再比较件数和余量 | 同时改变决策粒度与第一目标 |
| 覆盖封顶与厨具限制 | 达到三个喜好后节省食材，并比较有限厨具组合 | 将边际收益与设备约束放进目标，而不是继续堆高分数 |
| 结果验收 | 对具体角色、流行状态和厨具配置比较版本差异 | 排版变化应与算法变化分开，结果差异应能追查到规则或平局处理 |

保结果提速是与上述模型演进并行的要求。原型采用过候选复用、得分上界、λ 判定与缓存、厨具预计算和 CPU Worker 分块；这些机制分属不同分支，不都存在于最终执行路径。硬件背景、过滤与剪枝的区别、进度及导出验收见[CPU 求解复盘](prompt-journey.md#并行主线在-cpu-上求得更快同时保持结果)。

历史版本包含按标签分配订单的多方案模型，也留下过两阶段搜索等尝试。它们用于解释需求演进，不应混写成当前单客方案规划器的全部功能。本次作品集整理还具体核查了“等价食材”的供给反例：基础配方已经消耗某种食材时，继续追加它可能比改用标签相同的另一种食材更紧张，不能只按原始日供给选代表。这项核查属于此次整理，并非历史 prompt 已经证明的结论。

更完整的游玩问题、prompt 要点与取舍变化见[我的需求演进复盘](prompt-journey.md)。

## 我的工作与 AI 协作

历史记录支持我的主要工作包括需求定义、标签和禁忌语义澄清、指标优先级、厨具约束、具体角色案例验收，以及对版本结果差异的追查。标签数据取自他人项目；价格、供给和委托相关数据由我手动记录并计算期望。大量代码实现和部分调试使用了 AI 辅助。

本次作品集整理是在历史原型基础上进行的工程整理：明确主入口，拆分数据解析与规则职责，使用名称关联数据，补充针对规则边界的验证，并制作合成演示数据和文档。这些整理工作单独说明，不追溯为历史版本已经具备的工程化成果。第三方组件和参考材料见[来源说明](../THIRD_PARTY_NOTICES.md)。

公开样例的作用是让读者复现规则与取舍，不是提供完整游戏攻略。目前没有据此宣称游戏内收益提升比例、统计显著性或全局最优策略。若继续扩展，我会先补齐采样记录与游戏内对照，再研究多顾客共享库存、订单分布和酒水搭配，而不是直接把逐客余量解释成完整经营最优化。
